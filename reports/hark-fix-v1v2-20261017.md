## 2. 根因（统一处理）

旧框架把变异源码 `exec` 到新命名空间：
- V-1：phase4 新建 `types.ModuleType`。
- V-2：jh006 用 `dict(live.__dict__)`。

由此产生两个问题：
1. **类身份分裂**：变异模块重新定义了 `PathBoundaryError` 等异常类，消费者（orchestrator）仍按 live 类捕获。
2. **patch 目标落空**：测试对 `src.xxx.<attr>` 打的 patch 只作用于 live 模块，到不了变异命名空间。

此外：
- phase4 把 errors 计为检出（`failures or errors`），且不跑基线。
- jh006 只有一轮全局对照，没有逐条恒等对照。

修复方式：
- 每条变异的每次运行，都在**一次性仓库副本**的**独立 Python 进程**中执行。变异直接写到副本的源文件上。
- 这样变异模块、全部消费者和测试模块共享同一个导入图：每个异常只有一个类身份，每个 patch 目标只有一个模块属性。
- 原仓库只读（回归测试中有字节比对断言）。
- 两个脚本各内嵌同一份框架代码，以免新增文件超出范围。

## 3. 判定口径

每条变异跑三次目标测试：
1. **基线**：未改副本，必须 pass，否则记 `baseline_not_green`。
2. **恒等**：锚点替换为自身，走同一写入路径，必须 pass，否则记 `identity_not_green`。
3. **真实变异**：只有断言失败才记 `detected`。

以下情况一律不计为检出：
- error、skip、加载失败、测试数不为 1；
- `expectedFailure` 标记；
- **仅错误文字变化**：assertRaisesRegex 或 assertRegex 不匹配；或者失败源码行是对 error_info、exception、reason、message 文本的 assertIn/assertNotIn/assertRegex。

退出码：
- 0：全部检出；
- 1：存在存活、未检出或框架错误；
- 2：无存活，但有基线不绿（平台阻塞）。
