## 1. 方向与编号

Codex 是主要入口和基础工作环境，JH 提供上层协作与项目管理增强。基础 Coding、文件、Shell、Git、上下文与工具能力优先复用宿主。

四个产品分组 P1—P4 下设八个开发阶段 N1—N8。旧八阶段仅以 E1—E8 引用历史，停止作为后续执行排期；历史验收与安全约束继续有效。

不预设未经测量的工期。每阶段通过交付、独立审查和必要的架构裁决推进。

## 3. P1 的实施范围

### N1：先证明 Codex 内接入

1. 列出 Codex 原生承担、JH 必须新增、需要最小封装和暂缓的能力，并给出实际场景依据。
2. 优先验证 Skill + 现有 CLI；确实需要独立工具接口时再评估 MCP。最终形式通过接入验证与 ADR 记录，不凭名称认定完成。
3. 明确跨模型调用、结果收集、任务接续和用户可见输出如何进入当前 Codex 工作流程。
4. 复核现有文件工具批次：保留独立审核绑定、受控应用或恢复确实需要的部分，避免扩展通用工具平台。
5. 验证实际执行边界。Skill / Prompt 是流程说明；硬权限必须由宿主或受控执行接口落实。JH 的状态或批准记录不会自动接管全部宿主工具。
6. 现有 Provider 适配、任务存储和控制规则优先复用；不重建独立 UI 或完整自主 Runtime。

N1 完成需要有真实接入演示与证据；只增加说明文档不算完成。当前代表任务限定为上述 ADR-0004 的生成产物模板，自动文件应用待准入；这不改变下文 N2 的完整交付要求。

### N2：完成可使用的 MVP

最小闭环：

用户在 Codex 提出目标 → 规划与资源选择 → Gemini 执行 → Muse 独立审核 → Codex 根据反馈修正或应用 → 验证 → 交付。

至少覆盖本地代码修改和资料整理 / 数据转换两类代表任务。具体夹具、检查命令与预期结果在实施前确定，不以模型自评分替代检查。

必要证据：

- 正常真实双模型任务交付。
- 审核退回后的真实修复与重新审核；如果使用注入缺陷，明确标注夹具，保留前后产物。
- 审核关联当前任务、尝试和产物内容；产物改变后旧审核不能继续作为放行依据。
- 所有必需验收条件均有证据并通过，独立审核有效，且没有未解决的权限、预算、用量或副作用不确定问题。
- 模型不可用、预算不足、非法输出和用户取消等分支不会被误报为成功。
- 新会话可查询必要任务记录；不要求实现完整长期项目管理或长期后台运行。

已有真实证据可复用，但要说明它覆盖的条件与缺口。旧 E3 证明的双模型链不能单独证明 Codex 内完整产品体验。

P1 暂缓：独立 UI、完整自主 Runtime、完整经验学习、全天候云端运行、系统级自我修改。第一版调度采用明确规则和预算，不提前建设自学习路由。

## 4. P2—P4 的边界

P2 增强项目级目标和推进，不重复维护 Codex 的全部会话历史。复用现有 SQLite，先支持一个项目的可靠续接，再扩大范围。

P3 将已有任务审核与日志发展为可比较的评测和审计体系。经验先作为候选，验证后才进入适用范围明确的复用。单次成功不能推出通用成功率。

P4 在已有基础恢复上增加长期运行能力。优先复用可用宿主能力；更复杂协作只有在任务收益得到验证时再引入。流程优化保留版本、评测和回滚，按既有授权生效。

基础权限、预算、审核、错误记录和有界修复从 P1 就生效，不推迟到 N5 或 N7。
