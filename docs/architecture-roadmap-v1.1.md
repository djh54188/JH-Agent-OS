## 1. 架构结论

保留项目定位与 Meta Planner / Orchestrator / Worker / Reviewer 四层架构。优先验证可靠的任务生命周期闭环，然后扩展工具、经验学习、专业 Agent 协作和流程优化。

当前会话承担 Meta Planner / Architect 职责：设计边界、协议、路线图与验收条件。这一职责约定不代表 Gemini、Muse 或独立部署的 JH Runtime 已经接通。

项目目录检查结果：只有 `.git` 元数据，没有现有应用代码，因此本路线图从零开始。

## 2. 对 v1.0 的必要修订

### 2.1 明确 Codex 与项目控制层的边界

“Codex 为内核”保留为产品方向，但实现时区分三部分：

- Codex：所选接入方式提供的 Agent 运行、工具、事件与交互能力。
- JH 控制层：项目自有的协议、任务状态、路由规则、工具策略、预算、审核门槛和持久化逻辑。
- Provider Adapter：Gemini、Muse 和需要程序化调用的 Meta Planner 的模型适配器。

不要假定 Codex 原生自动提供项目要求的跨供应商调度、SQLite 记忆或业务风险规则。阶段 1 必须选定并验证具体接入方式。

OpenAI 官方文档说明，Codex SDK 可程序化控制本地 Codex Agent；App Server 可用于处理认证、会话历史、审批和流式事件的自定义客户端。官方也区分托管 Codex harness、自应用 Agent 循环以及直接模型调用。接入选择应记录为 ADR，避免同时维护多个运行入口。

来源：[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)、[Agents 运行方式](https://developers.openai.com/api/docs/guides/agents)。

建议调用路径：

```text
用户 → Codex 入口 → JH 控制层
                      ├─ Router / Risk Policy
                      ├─ Provider Adapters → Worker / Reviewer / Meta Planner
                      ├─ Tool Executor → 受限工作区
                      └─ Task Store / Audit Log / Memory
```

控制层与 Codex 可以通过所选接口双向交换事件；上图表示职责关系，不规定全部调用都必须同步串行发生。

### 2.2 将“智能建议”和“执行权”分开

Worker 生成计划、内容、补丁或结构化工具请求；工具执行器校验权限并实际执行。Reviewer 输出质量结论与证据；权限和任务最终状态由控制层规则决定。

模型角色与具体型号分别配置。Gemini 是首选 Worker、Muse 是首选 Reviewer，是否长期采用由项目任务集的实测决定。Muse 的供应商、API 地址、模型 ID、认证方式、结构化输出与工具能力尚未提供，应在阶段 1 核实。

Meta Planner 初期通过当前架构师会话参与。自动化升级若需要调用 Meta Planner，应另行验证其 API、认证与成本。GPT-6.1 Sol 的官方模型 ID 为 `gpt-6.1-sol`，工具调用使用 Responses API；这不代表当前账号或本项目已经配置了可用凭据。

来源：[GPT-6.1 Sol 模型文档](https://developers.openai.com/api/docs/models/gpt-6.1-sol)。

### 2.3 修正 Router 分级

Risk、Complexity、Uncertainty 分别记录，附判断依据。复杂度和不确定性用于选择规划深度、审核要求和升级路径；风险用于限制权限与决定是否需要特定动作的用户授权。

| 路由 | 建议适用范围 | 必要行为 |
| --- | --- | --- |
| L0 | 低风险、目标清楚、简单任务 | Worker 执行，MVP 阶段均经过独立 Reviewer |
| L1 | 低或中风险，需要多步执行 | Worker 计划、受控执行、独立审核 |
| L2 | 架构、战略或高不确定性任务 | Meta Planner 规划，再交给执行闭环 |
| L3 | 命中危险动作规则 | 具体方案与影响可审查；核对现有授权；缺少必要授权时等待用户；准备恢复措施；执行与验证 |

L3 优先于其他路由。不得通过加权平均把危险动作降级。模型可提出分类建议，但危险动作规则由代码执行。

检查任务入口和每一次工具调用：目标路径、操作类型、实际参数、外部接收方及权限变化都可能改变风险。计划改变后，仅对超出已有授权的动作重新取得授权。

备份只适用于可备份对象。外部发送、支付等动作可能无法完整撤销，应在执行前明确影响，不能一概承诺回滚。MVP 排除这些不可逆动作。

### 2.4 完整定义任务生命周期和失败路径

状态候选：`created`、`classified`、`planning`、`awaiting_approval`、`executing`、`reviewing`、`repairing`、`succeeded`、`failed`、`cancelled`、`needs_attention`。

状态机必须声明合法转换、终态和恢复条件。任务记录至少包含：版本、任务 ID、目标、验收条件、约束、当前状态、风险依据、路由依据、产物引用、工具执行证据、审核结论、预算与错误信息。

默认闭环：

```text
输入 → 分类/规划 → 受控执行 → 独立审核
                              ├─ 通过 → 记录日志/候选记忆 → 返回
                              ├─ 可修复 → 有限修复 → 再审核
                              └─ 耗尽预算/无法判断 → 失败或需要处理 → 返回原因
```

规划默认值：最多 2 轮修复；模型调用另设有限重试、总预算和总截止时间。默认值必须可配置，待评测调整。

Worker 完成不等于任务成功，Reviewer 不可用不能自动视为通过。模型自报的 `confidence` 只能作为辅助信息，不可代替验收条件或可验证证据。

### 2.5 独立审核必须有验收证据

Reviewer 获得原始目标、验收条件、必要上下文、实际产物及工具/测试证据。Worker 的摘要只能辅助，不能作为唯一依据。禁止 Worker 修改审核结论或绕过审核状态。

审核输出：`pass`、`revise`、`reject` 或 `needs_human`，并包含问题、严重程度、证据引用和建议修复。

写入类任务先在隔离工作区或暂存区形成产物，审核通过后再通过受控动作应用。需要外部发布的任务在发布前审核。文件写入成功、Shell 退出码为零、Git 提交成功均不单独代表满足用户目标。

### 2.6 结构化协议允许自然语言内容

强制结构化的是通信信封、类型、状态、权限、结果与证据。`goal`、`summary`、`findings` 等字段可包含自然语言。

JSON Schema 定义版本与验证规则；非法 JSON、缺失字段、未知工具和越界参数必须拒绝或进入有预算的纠正流程。JSON 外观本身不能保证语义正确或权限有效。

### 2.7 日志与长期记忆分开治理

- 日志：记录成功、失败、取消、审批和审核事件，支持追踪。
- 长期记忆：保存经验证的偏好、环境事实、项目状态、决策和经验。

SQLite 作为 MVP 持久化来源；按 `user_profile`、`environment`、`projects`、`decisions`、`experiences` 分类。目录可作为文档与导出视图，避免数据库和目录各自形成冲突的权威记录。

记忆记录包含来源、验证状态、适用范围、版本及复核时间。失败结果只能形成带失败证据的候选经验；不得自动升级为正确事实。API 密钥不得写入日志或记忆。未经统计的经验不标注“成功率 92%”等数字。

自优化必须先离线验证、保留版本和回滚路径；运行中的 Agent 不得自行放宽权限或修改审核门槛。

## 3. 八阶段路线图

顺序推进，以交付物和验收条件为门槛，不预设未经测量的工期。每阶段应记录架构决策和未解决事项。

### 阶段 1：架构契约与接入验证

目标：把角色和接口约定变成可实施设计。

交付：

- Codex 接入 ADR、职责边界与部署范围；MVP 默认单用户、本地运行、串行任务。
- Task、Plan、ToolRequest、ToolResult、ReviewResult、MemoryRecord 的版本化 Schema。
- Worker / Reviewer 适配器契约；Meta Planner 人工介入路径。
- Gemini、Muse 的供应商、模型 ID、端点、认证与可用能力清单。
- MVP 验收任务及危险动作清单。

验收：所选 Codex 接口可产生与接收任务事件；两家供应商各完成一次最小真实请求及输出解析；关键能力缺失时记录明确替代或范围调整，不能把 Mock 当作真实接通。

### 阶段 2：任务控制层、Router 与持久化

目标：先让任务状态和策略运行正确。

交付：Orchestrator、合法状态转换、规则式 Router / Risk Policy、SQLite 任务与事件表、任务 ID、基础日志、Mock Provider 与 Mock Tool。

验收：成功、失败、取消、等待授权、预算耗尽均能进入正确状态；无效消息被拒绝；危险动作不能降级；进程重启能恢复任务记录。尚不能证明安全重放的动作不得自动重放。

### 阶段 3：真实 Worker / Reviewer 闭环

目标：形成真实双模型执行与审核流程。

交付：Gemini Worker、Muse Reviewer、Schema 校验、有限修复、API 错误处理、审核产物与证据引用、基础项目记忆写入。

范围：先做无外部副作用的文本整理、数据转换与补丁生成。

验收：真实调用完成“输入 → 路由 → Worker → Reviewer → 记录 → 返回”；故意植入错误能产生驳回或修复；Reviewer 超时、非法 JSON、供应商拒绝和超预算不会被标记为成功。

### 阶段 4：受控工具与 MVP 验收

目标：获得最小行动能力并完成 v0.1 MVP。

交付：限定工作区的文件读写；参数化、允许列表内的 Shell 工具；Git 状态、差异和隔离分支/暂存产物；逐调用风险检查；必要授权事件；恢复记录。

范围：本地文件任务和简单代码修改。任意 Shell、系统权限修改、外部消息发送及不可逆发布排除在 MVP 外。

验收：固定至少 30 个案例，覆盖正常流程、审核拒绝、越界路径、预算耗尽、供应商故障和写入中断。所有控制与权限案例必须通过；质量案例报告成功率和失败原因，不能以平均分掩盖权限失败。至少完成一次从失败写入恢复的演练。

里程碑：真实模型 + 受控工具 + 独立审核 + 持久记录的 v0.1 闭环。阶段 1—4 是首轮开发范围。

### 阶段 5：可靠性、成本与可观测性

目标：使闭环适合持续使用。

交付：请求超时、有限重试、限流处理、成本预算、追踪、调用与审核指标、故障注入、恢复与副作用对账。

验收：重启、断网、限流及 Worker / Reviewer 不可用时状态可解释且预算有界；不确定是否已生效的动作进入对账或人工处理，避免盲目重放。供应商计费无法精确获得时，明确区分估算与实账。

### 阶段 6：可验证的记忆与经验复用

目标：让记忆改善执行质量。

交付：六类信息的查询/更新/导出、来源与版本、候选经验验证、冲突处理、删除/失效机制、按任务检索和上下文预算。

验收：对同一固定任务集比较启用和关闭记忆的结果；报告质量、成本与错误记忆影响。过期或冲突信息能复核；改善不足时保留简单记忆，不自动扩大使用范围。

### 阶段 7：专业 Agent 协作

目标：在稳定控制层上增加专业执行能力。

交付：代码、研究、数据等专业角色；子任务图；受限并发；依赖管理；结果汇总；共享资源锁；独立审核边界。

验收：并发任务不会互相覆盖文件、绕过授权或覆盖审核结论；汇总结果符合总任务验收条件；用同一任务集比较单 Worker 与协作方案的质量、耗时和成本，证明适用场景。

### 阶段 8：受控流程优化

目标：基于证据改进路由、提示词和经验策略。

交付：版本化配置、优化建议、离线评测、受限试运行、变更记录与一键回滚。

验收：每次优化说明相对基线的收益、退化与成本；关键控制与质量用例无不可接受退化；涉及权限、预算上限或审核门槛的变更按现有授权流程处理。

## 4. 架构师职责与下一步

Meta Planner 在架构定稿、路由升级、重大失败复盘以及阶段验收时介入。日常执行由 Worker 承担；独立质量审核由 Reviewer 承担。

下一步从阶段 1 开始：选定 Codex 接入，补齐 Muse 接口信息，定义协议与验收案例，然后验证最小真实调用。八阶段中的“自优化”与多 Agent 不应提前挤占 MVP 闭环的开发范围。
