## 1. 成功条件应使用明确的逻辑关系（优先级 P1）

已确认：docs/danger-action-policy.md:33 使用“Reviewer pass 或满足 acceptance_criteria”；路线图要求独立审核闭环。docs/mvp-acceptance-cases.md:45 还将模型自评分 >=85 放进验收条件。

风险：两种实现都可能认为自己符合文档，一个将测试通过作为绕过审核的条件，另一个只看模型 verdict。评分可以辅助排序，不应单独使任务成功。

建议提交架构师确认后统一为：
- 当前产物的有效独立审核为 pass；
- 所有必需验收条件有对应证据并通过；
- 没有未解决的权限、预算或执行结果不确定问题；
- 控制层才允许转为 succeeded。

这是规范澄清建议，不在本文件中直接更改现有安全规则。已有流程不得因本文件新增绕过途径。

验收对应：OPT-01、02、03、07。

## 2. 审核必须关联到具体任务、尝试和产物（优先级 P1）

已确认：review_result.v1.json 约束字段形状，但不同 task_id、pass 同时包含 p1_critical 问题、反向行号范围都能通过现有 Schema。Responses 适配器执行 JSON Schema 校验；它不负责判断响应属于哪个运行中的任务。

这证明“格式合格”不足以代表“可以用于本次成功裁决”，不证明正在开发的 Orchestrator 已存在放行漏洞。

最小建议：
- 控制层维护可信的 task_id、attempt_id、artifact_version/sha256；
- 发送审核时记录这些信息；接收时先校验关联，再接受 verdict；
- 同一路径内容变化后，旧审核不能继续有效；
- 旧 attempt 的迟到结果不得覆盖新结果；
- pass 与未解决严重问题并存时，记录矛盾并进入受控处理；
- 核对证据引用与行号范围。

先使用可信的控制层记录和调用包装信息，不必立即破坏现有 ReviewResult Schema。若增加协议必填字段，按版本与兼容策略单独实施。

验收对应：OPT-04—08。

## 3. 工作区路径判定需要验证真实归属（优先级 P1）

已确认：docs/danger-action-policy.md:72 将“以 workspace_root 为前缀”作为判定条件之一。离线探针证明 D:\\JH-Agent OS-archive\\notes.md 能通过简单 startswith 检查，但不属于 D:\\JH-Agent OS。

建议：按规范化的路径组件判断工作区归属，处理盘符与大小写；对真实工具在调用前解析链接/父目录。对于尚不存在的文件，校验已存在父目录和待创建的文件名。普通路径字符串校验不能证明 junction 的最终目标安全。

阶段 2 使用 Mock 验证策略分支；真实 junction、写入原子性和竞争窗口验证留在阶段 4。此项不要求现在引入任意 Shell 或真实写入工具。

验收对应：OPT-10—16。

## 4. 模型容量与任务额度应分别计算（优先级 P1）

已确认：Responses 适配器自身以配置的 131072 为输出上限；任务 Schema 另有 max_tokens 与时间预算。适配器接口目前未定义剩余任务预算如何传入。

建议控制层在每次调用前计算可用预算，并通过每次调用的参数传入：
- 调用截止时间不得晚于任务截止时间；
- 输出额度不得超过模型上限及任务扣除输入预留后的剩余额度；
- 重试、修复和再次审核共用原任务预算；
- 未获得 token 用量时记录 unknown，不能按零消耗继续无限调用；
- 输入估算与实账分开记录；估算不足以支持硬额度保证时，应明确限制或受控停止。

例：剩余 20000，输入预留 644，输出最多 19356。这个算式用于验收夹具，不是实际生产输入 token 数。

验收对应：OPT-17—22。

## 5. 避免把规划层级与动作权限混为一个字段（优先级 P2）

已确认：路线图的 L3 表示危险任务的规划/授权流程；危险策略中的 Level 3 表示绝对禁止。两者命名相似、语义不同。

建议保留现有兼容字段，在控制层明确区分：
- route_profile：选择规划深度与模型角色；
- action_policy：根据实际工具参数决定允许、需要授权或拒绝。

规划层级不能增加工具权限。模型填报 risk_level/requires_human_approval 仅作为待验证信息。

另一个范围冲突：docs/mvp-acceptance-cases.md:4 将 MVP 写成阶段 2—3；路线图将完整 v0.1 MVP 验收点设在阶段 4。建议实施文档修订时同步标注阶段 2 控制层验收、阶段 3 真实模型闭环、阶段 4 完整 MVP。

验收对应：OPT-09—11。

## 6. 将重启恢复写成可验证的不变量（设计建议）

持久化正在开发，本次不对其实现结论作判断。建议至少满足：
- 同一次状态改变和对应事件同事务提交；
- 同一 event_id/attempt_id 只应用一次；
- 重复领取同任务时最多一个有效执行所有者；
- 终态不会因重启倒退；
- 不确定是否已产生副作用的动作不能盲目重放；
- 不能仅凭旧 PID 终止或接管进程。

优先使用项目现有 SQLite 和事务机制实现最小约束，不为此增加消息中间件或完整事件溯源框架。

验收对应：OPT-23—28；供应商异常对应 OPT-29—30。
