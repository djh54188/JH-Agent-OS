# JH-Agent OS 协作规则

版本：v1；日期：2026-10-18；状态：用户已批准，适用于后续派单。
入口：[AGENTS.md](../AGENTS.md)；模板：[执行任务模板](templates/execution-task.md)。

## 1. 范围、职责与环境

1. 一条派单只包含一个实施范围，用本轮完整指令替换旧指令，不在旧长提示末尾追加冲突范围。交付第一行写一句“范围理解”；发现范围冲突时先指出，继续可独立完成的已授权工作。
2. 派单固定规则路径、版本和提交（未提交时用文件 SHA-256），另列代码基线、工作树或云端仓库/分支，以及本轮增量。规则的版本号不能代替可读取的正文。
3. 架构师负责规划、独立复核与验收，执行 AI 负责实现、完整验证和提交；执行应用/模型可替换。执行自检不能批准自己的交付。
4. 本地真正工作树为 `D:\JH-Agent OS\data\worktrees\n1-artifact-entry`，分支 `n1-artifact-entry`。原树 `D:\JH-Agent OS` 的旧失败 WIP 不重置、不清理、不混入；开始工作先核对 HEAD、状态与有关差异，不覆盖并行工作。`docs/review-backlog/hark-pilot-20261017/` 三份用户确认归属的归档保留，不自动加入功能提交。
5. Hark 只能操作 GitHub 仓库副本，不能操作本地 Windows 工作树；云端提交、Windows 本地验证、合入和发布分别报告。同步以明确授权和固定提交为准，不整分支覆盖当前实现。
6. `production complete`、`FileToolExecutor` 自动应用继续关闭；默认 Codex 主控和指定架构审查会话不被隐式替换。具体能力和阶段状态以最新裁决为准，不在本规则中复制一套动态状态。

## 2. 裁决承接与偏离

1. 每批列“承接裁决 / 已关闭，不重做 / 本批只做 / 本批不做”。已关闭项不重复整改；新的可复现反例影响本批范围时，提交依据重新裁决。
2. 修改已验收测试、守卫或契约，改变字段语义，删除既有函数，均列入偏离清单，说明原行为、新行为、原因、影响及验证。无偏离写“无”。不得自行宣称修改等价或“更强”。
3. 已授权范围内可完成候选修改与验证，交独立审查裁决；扩大授权、放宽成功门或改变本批范围时，先停止相关动作并说明原因，不把每个普通实现选择变成请示。
4. 字段保留旧名却改变语义时，须明确记录为技术债，说明消费者影响和暂行解释；本批未授权时不顺带重命名或扩建迁移机制。

## 3. 按故障类验证，避免只修一个样例

1. 实现前先写本批必须维持的不变量，列出直接相关的输入空间和故障类；附已知反例的只读路径。执行方须补自建反例，不能只针对评审给出的字面样例修补。
2. 故障类覆盖表列：类别、输入/注入、预期行为、证据位置、已覆盖或已知未覆盖及原因。每项通过条件可检查，例如“拒绝、零外部调用、源文件字节不变”，不只写“有意义的正反控”。
3. 登记恢复类可按可读性、解析、字段形状、跨记录一致性、事件顺序、幂等绑定等层次分析；只处理本批相关且有依据的类别。示例不是确认缺陷清单，也不要求穷举所有组合或扩建完整平台。
4. 评审探针与原始结果保留原样；复跑使用副本并写入新的证据目录。整改前后用同类输入对照；守卫变异必须证明削弱守卫会导致相应检查失败。

## 4. 证据、数字与平台

1. 原始证据保留原字节，不为符合新规则改写旧证据。新生成的文件证据明确编码/换行，以字节写入；回读实际磁盘字节核对摘要、大小及适用的帧数。摘要匹配只证明字节一致，不自动证明来源可信、关联正确或证据完整。
2. 计数以测试运行器的发现/实际运行结果为主要依据，AST 或其他独立路径辅助复核，不用 grep 作为权威测试数。动态生成、参数化、继承等导致差异时解释原因，不为凑数修改统计。
3. 每项结论性数字提供原始日志路径及提取命令或带版本的提取脚本；明确总数、通过、跳过、错误、冗余及未确定项，按实际适用口径报告。
4. 协议调用数、派发数、执行次数和验收成功数分别计数；例如 initialize/thread-start/turn-start 三次协议调用可属于一次派发。
5. 报告写明平台、解释器及相关应用版本；Windows 与 Linux、不同 Python 版本的结果分别记录。临时目录、路径和权限 workaround 明示，不当作产品能力。
6. 文件日期与实际取证日期有差异时注明缘由；缩写首次出现给出定义或可定位的引用。

## 5. 分级结论与真实调用

1. 分别报告“实现完成 / 离线通过 / 真实路径通过 / 待独立验收或已按指定范围验收”；每项绑定代码提交和证据源提交。线程恢复、桌面指定会话唤起、审查开始并返回分层报告，前一层不能代替后一层。
2. 发送成功、执行方 declared_complete、历史运行记录或模拟数据都不授予任务成功。成功仍须当前有效独立审核、必需验收证据和权限/预算/副作用条件同时满足；未知用量及不确定副作用不得自动重放或自行解除。
3. 先核实实际应用能力再选型；等待有界，不自动重试不确定派发。未实测的能力声明不支持；指定会话状态不明时不发送，不另建架构师会话补成成功。
4. 按变更影响决定是否调用真实模型。仅改校验且不改变已核实真实路径时可沿用原证据，注明源提交和适用范围；改变协议、实际请求或运行路径时重新判断所需实测，不能仅凭“只改校验”免测。
5. 验证器结果如实分类，exit 1 可表示执行完成但诊断通过条件未满足，不为凑全绿改规则。已知误报工具只提供诊断证据，不单独支撑验收，不恢复旧 12/12、19/19 等被撤回的结论。
6. 新增或修改错误类型时，按实际拒绝原因区分寻址、请求约束、登记不可用等，不顺带大改既有错误体系。

## 6. 生效与维护

本规则从下一批派单起使用。当前进行中的 GUI 只读运行记录批保持原授权范围；不追加推测性整改，不因本规则重跑已完成验证。规则采用和代码问题修复分别交付。

规则增改由用户裁决。仅修改本项目规则不代表全局 `D:\AGENTS.md` 已更新，也不代表 GitHub 或其他会话已同步。执行方按明确指令单独提交规则文档，避免混入并行功能提交。
