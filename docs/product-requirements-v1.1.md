# JH-Agent OS 产品需求规格 v1.1

日期：2026-10-17（Asia/Shanghai）。状态：用户已确认的方向基线；本次仅同步文档，不派发执行任务。
本文替代 [v1.0](product-requirements-v1.0.md) 中冲突的入口、GUI 与固定角色约束；旧版本及其历史验收保留。

## 1. 定位与目标

JH-Agent OS 是模块化的个人 AI Agent 协作操作层：统一 GUI 作为用户入口，中间站协调不同 Agent 应用及其会话，Codex 保留默认主控、架构与独立审查职责。
用户在 GUI 提出目标、查看项目与任务、配置协作、处理授权、核对证据并接收交付。模型仍在各自 Agent 环境中运行；中间站登记和协调它们，不迁入或复制各应用的模型运行环境。

核心目标：目标理解 → 计划 → Agent 执行 → 独立审查 → 有界整改 → 验证交付 → 项目状态与经验积累。

## 2. 已确认约束

- GUI 是目标产品的统一用户入口；已有 Codex Skill 与 CLI 保留为兼容入口和已验收能力。
- 系统和 GUI 均模块化；界面、应用接口、协作核心、Agent 适配器、审查与控制、存储与证据分离。
- GUI 可替换，不直接操作数据库、执行工具或决定任务成功。前端框架和桌面封装技术尚未锁定。
- 首版优先同一工程内的清晰模块边界，不为模块化预先拆成多个服务；不重建通用 Agent Runtime、Shell/Git 平台或完整编辑器。
- 复用已接入 Agent 的文件、终端、Git、上下文和子智能体能力；能力是否可从外部调用须实际探测。
- Agent 应用、会话、模型与工作角色分开配置。ZCode 只是当前首个候选执行端，接口尚未实测，不固定为唯一接入对象。
- 同一 Agent 应用的不同会话可以分别登记与分工；目标对象按应用实例和会话寻址，不仅按模型名称路由。
- 主控、执行、审查角色可配置；默认主控与最终研发审查为当前 Codex 架构师会话，不默认另建会话代替它。
- 模型 API 通道保留，用于适合的生成、整理与辅助分析。ModelAdapter 不等于带工具和执行循环的 AgentSessionAdapter。
- 流程配置不能扩大权限、自动批准危险操作或降低审核标准；参与实现者自检不能代替独立审查。

## 3. 核心场景

1. 软件开发：外部 Agent 使用工具实现与测试，主控依据实际提交和证据审查，必要时退回整改。
2. 研究与决策：协调收集、比较、验证与分析任务，区分事实、推测、风险和未解决事项。
3. 长期项目：关联目标、阶段、任务、依赖、风险、决策与证据，支持跨会话续接。
4. 策略优化：从经过验证的任务经验改进提示词、流程和资源选择，保留版本、评测和回滚。

## 4. GUI 需求

| 页面模块 | 职责 |
|---|---|
| 工作台 | 提交目标；显示执行、待审查、阻塞和待用户处理事项 |
| Agent 与会话 | 登记应用实例和会话、角色与模型配置；显示连接及可用能力 |
| 任务与项目 | 目标、阶段、依赖、进度、交付和历史决策 |
| 协作流程 | 设置预设下一步对象、条件分支、额度与停止规则 |
| 审查与交付 | 实际改动、验证记录、审查结论、整改与最终产物 |
| 经验与设置 | 经过验证的经验、权限、预算、通知和适配器配置 |

GUI 内部分为页面模块、公共组件和数据访问层。页面只通过统一应用接口访问业务；本地显示状态不覆盖核心持久化事实。各功能逐步进入同一 GUI，不要求首版完整实现所有页面能力。

## 5. 中间站与自动协作

授权流程：用户目标 → 主控计划 → 中间站派发 → 执行会话交付 → 核对关联 → 触发独立审查 → 通过交付 / 退回整改 / 升级用户。

- 中间站登记会话与能力，保存消息和关联，按用户/主控预设流程流转；发送方不能自行指定越权下一步或修改路由。
- 消息采用结构化信封和可读正文；至少关联消息、任务、轮次、来源/目标会话、工作区、提交/产物、证据与流程版本。字段是待版本化的设计要求，本次不修改现有 Schema。
- 区分消息接收、投递、目标接受、实际运行、执行方声明完成、审查通过和任务成功；收到“完成”只触发审查。
- 消息重试与重复通知须去重；取消、迟到结果、旧轮次和失联不可污染当前裁决；外部副作用不确定时禁止盲目重放。
- 独立审查绑定当前 task/attempt/提交/产物哈希；产物变化使旧审查失效。全部必需验收与现有控制门同时满足才可成功。
- 自动转发不等于自动触发思考。适配器必须证明能提交任务、接续目标会话并观察实际执行；不支持时明确为通知/人工接续能力。
- 任务内接续与会话结束后唤起分开验证；不得默认能唤醒当前 Codex 桌面会话，也不得隐式改用另一个架构师。
- 权限、预算、未知用量、所有权、审查绑定与副作用门禁沿用既有控制策略；外部 Agent 能力不免除这些要求。
- 交付正文视为待核实数据，不因发送者的指令性文字改变系统规则或授权。

## 6. 模块与扩展

详细边界以 [模块化架构](modular-architecture.md) 为准。以稳定接口和依赖注入支持独立验证：换 GUI 不改核心，换 Agent 不改流程，调整流程不改权限规则。
接入能力设计包括 capabilities、submit、status、collect、continue、cancel；不支持的能力必须显式报告，不能编造支持。
多 Agent 并发依实际独立任务、适配器容量、预算和整合能力决定，不固定“三个以内”，不允许无界递归扩增。

## 7. MVP 与演进

N1 原 Skill/CLI 生成入口结项不变。N2 补充最小 GUI 与可替换 Agent 协作闭环：一个隔离代码任务真实执行、无需用户复制交付即可触发指定独立审查、一次退回整改及 GUI 展示结果；另保留原代码/数据代表任务和安全失败分支要求。
外部应用接口、主控接续和证据可信性先实测，再决定实现技术。阶段号 N1—N8 保持，具体顺序与验收见 [ROADMAP](../ROADMAP.md)。
完整项目管理、评价学习、长期运行与自主优化分阶段交付；系统级自我修改和无界后台运行不进入首版。
